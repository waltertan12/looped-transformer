# H13 / H14: operator labels and addition-only / subtraction-only test sets (design)

_Approved by Walter 2026-11-23 ("yea that checks out"). Small change: short design._

## Why
D-012 says "loops buy steps, weights buy arithmetic". The arithmetic half is fuzzy: is it number
size, or the lookup multiplication needs? H13 tests that with test sets that have no `*`; H14
checks whether operator mix predicts errors beyond depth and number size. Both use the 12 saved
D-012 checkpoints: **no training, training data unchanged.**

## Goals / non-goals
- Goals: operator labels on existing test results; new frozen test-only add/sub sets; a script
  that scores any saved checkpoint on any dataset dir; pre-registered rules; a short report.
- Non-goals: new training, new architectures, changing `data/nested_bal`.
- Anti-goal: H14 numbers that just re-measure number size (must compare within matched cells).

## Approaches
1. **Frozen test-only dataset + checkpoint scorer + analysis script (chosen).** Matches the
   project's "stable, pre-generated, verifiable data" rule; reuses checkpoints.
2. Generate on the fly at eval time: rejected (not stable / not re-checkable).
3. Retrain with new data: unnecessary for these questions.

## Design
1. **Operator labels (H14):** analysis script reads `data/nested_bal/test/*.tokens.npy`, counts
   `*`, `+`, `-`, `(` per question (prompt part only), joins to each run's `per_example.npz`
   by row order (the final dump uses the full test set in level order; script asserts the
   `answer`/`depth` columns match). Labels: `n_mul`, `n_add`, `n_sub`, `n_paren`, `mul_frac`.
2. **New test-only datasets** (built by a new `scripts/build_ops.py`):
   - Two dataset dirs, `data/nested_add` (only `+`) and `data/nested_sub` (only `-`), level = depth.
     Correction (planning): the generator never puts `+` on the right of `+`, so an add-only
     tree is a left-deep chain and depth = number of `+` = terms − 1 (it parses that way too).
     Add: depth 1–15 (2–16 terms) as far as the 80-char row allows. Sub: depth 1–8, parentheses
     keep nesting visible; n_ops uniform over the feasible range.
   - Inputs **exactly** k digits, k ∈ {1,2,3,4} (label `in_digits`; differs from nested_bal's
     "up to k"). ~1000 per (op, level, k) cell, skipping cells whose prompt exceeds 80 chars.
   - Same storage format; columns `answer, n_ops, depth, length, n_tgt, in_digits, ans_digits`;
     meta records overlap with `nested_bal` train at the same depth;
     deterministic seed; checked by `scripts/verify_data.py`.
3. **Checkpoint scorer** `scripts/eval_ckpt.py --ckpt ... --data ... --out ...`: loads a
   checkpoint, rebuilds ToyConfig, respects `reverse_answer`, scores at the run's training K,
   writes `per_example.npz` with all label columns. Reuses `dump_per_example` / `FrozenData`.
4. **Report** `scripts/ops_report.py` → `docs/results-ops.md`: accuracy by model × op × in_digits ×
   level, both seeds, deep − looped and %Gap; H14 tables within matched cells.

## Pre-registered rules
- **H13 supported** if deep − looped ≤ 0.03 on add and sub (averaged over 2–4-digit inputs,
  both seeds), versus +0.05…+0.15 on mixed data. **Rejected** if deep − looped ≥ 0.05: number
  size itself needs weights.
- **H14 supported** if, within cells matched on depth, answer digits and input digits,
  accuracy falls ≥ 0.05 from the lowest to the highest `mul_frac` third (both seeds).
  Secondary: does deep − looped grow with `mul_frac`?

## Left to the builder
Exact per-cell counts where cells are thin; `n_ops` choice per subtraction depth (uniform over
feasible); table layout of the report.
